# 資料結構：食材資料

## 分類架構
四大分類：蔬菜、水果、海鮮、肉品（可再細分次分類，例如海鮮下分魚類／甲殼類／貝類／頭足類）。

## 基本欄位（每筆食材）

| 欄位 | 說明 | 備註 |
|---|---|---|
| name | 中文名／俗名 | 市場常用俗名優先，例如「透抽」 |
| category / subcategory | 四大分類 → 次分類 | |
| image | 圖片 | 建議整體＋切面各一張 |
| months / seasonNote | 產季 | 蔬果海鮮用月份陣列；肉品多半全年供應，用文字註記即可，不必勉強套用月曆 |
| characteristics | 外觀特性、口感 | 2–3 句 |
| selectionTips | 挑選技巧 | 3–5 條，精簡條列，不寫長文 |
| nutrition | 營養價值 | 只列真正突出的重點，見下方「營養價值欄位的篩選原則」 |
| storage | 保存方式 | |
| spoilageSigns | 保存後如何判斷是否變質（看得出來的徵兆） | 選填，查證標準比其他欄位更嚴格，見下方「保存變質徵兆欄位」 |
| hiddenRisks | 無法靠外觀判斷、只能靠保存方式預防的風險 | 選填，跟 spoilageSigns 是刻意分開的欄位，見下方「隱性風險欄位」 |
| verification | 各欄位的查證狀態 | 分級定義見下方「資料驗證分級」 |

## 營養價值欄位的篩選原則

`nutrition` 不是欄位越多越好，也不要每筆資料都套用同一套「熱量／維生素C／鉀／膳食纖維」固定組合。

- **熱量一律列出**：作為基本資訊，即使沒有特別突出也保留（它是精確數值，不是模糊判斷）。
- **其餘欄位只列真正突出的 1–2 項，且必須用下方「官方宣稱門檻」判斷**，不可憑感覺或查證員主觀判斷「這個應該算高吧」。
- **「尚可」不是一個該出現在資料裡的值**：如果查證後發現某項營養素沒有達到門檻，代表這項不值得寫進 `nutrition`，而不是寫「尚可」交代過去。
- 若一筆食材查證後所有項目都不突出，`nutrition` 就只留熱量一項，這是正常情況，不用勉強找一個「重點」出來湊數。
- 每筆最多列 3 項（熱量 + 最多 2 項突出重點），若同時有多項達標，優先列「數值 ÷ 門檻」倍數較高的項目。
- 資料完全未經 TFDA 官方資料庫查證（`verification.nutrition.level` 為 `unverified`）時，即使要標註「感覺上」突出的營養素，也不可用「良好來源」「含量低」這種暗示已查證的字眼，一律用「推估含量較高／較低（未經官方資料庫查證）」這類明確標示為估算的措辭，避免使用者誤以為已查證。

### 官方宣稱門檻

門檻採用衛福部「包裝食品營養宣稱應遵行事項」（113 年 2 月 19 日修正）表四「來源／供給／含有」宣稱的標準（無特殊族群訴求適用，每 100 公克固體食品），這是台灣食品標示唯一有法規依據的門檻，不是我們自訂的：

| 營養素 | 門檻（每 100g） | 對應資料庫查詢欄位 |
|---|---|---|
| 蛋白質 | ≥ 6 公克 | 粗蛋白 |
| 膳食纖維 | ≥ 3 公克 | 膳食纖維 |
| 維生素A | ≥ 105 微克RE | 視網醇當量(RE) |
| 維生素C | ≥ 15 毫克 | 維生素C |
| 鈣 | ≥ 180 毫克 | 鈣 |
| 鐵 | ≥ 2.25 毫克 | 鐵 |
| 鎂 | ≥ 58.5 毫克 | 鎂 |
| 鋅 | ≥ 2.25 毫克 | 鋅 |

達標時一律標記為「**良好來源**」（不用「含量高」「含量極高」這種對應法規表三「高」宣稱的字眼，我們用的是門檻較低的表四「來源」等級，用詞要對應正確的等級，不要誇大）。

「低脂肪」比較特殊，用的是同一份法規表二「低」宣稱門檻（脂肪 ≤ 3 公克／100g），且**只在肉品／海鮮類別套用**——蔬菜水果幾乎天生都符合這個門檻，標了也沒有鑑別度，容易列出去也沒有意義。

**「鉀」不在這份法規的「可補充攝取營養素」清單裡**（清單是：蛋白質、膳食纖維、維生素A/B1/B2/B6/B12/C/D/E/K、菸鹼素、葉酸、泛酸、生物素、膽素、鈣、鐵、碘、鎂、鋅、氟、硒），台灣食品標示法規沒有「鉀含量高」這種宣稱的門檻依據，**不要用鉀作為判斷突出與否的依據**。如果想呈現鉀的數值，只能用中性方式（純數字，不加「高」「良好來源」這類評語）。

法規全文與完整表格（含孕乳婦、一至三歲等特殊族群門檻）可查詢衛福部食藥署官網公告「包裝食品營養宣稱應遵行事項」。

## 保存變質徵兆欄位（spoilageSigns）

回答「食材買回家、保存一段時間後，怎麼判斷還能不能吃」，是使用者實際會遇到的問題，但也是**資料錯誤後果最嚴重的欄位**（誤判「還能吃」可能造成食安風險），所以查證標準刻意訂得比 `selectionTips` 更嚴格。

### 結構

```json
"spoilageSigns": [
  {
    "sign": "薑的節末端摸起來軟爛、按壓會凹陷出水；環境潮濕時外皮可能長出白色絨毛狀黴菌；切開後內部出現發黑",
    "verdict": "discard",
    "source_url": "https://www.edh.tw/article/31427",
    "source_date": "2026-08-01"
  },
  {
    "sign": "僅長出芽點，薑體本身摸起來仍硬實，沒有軟爛出水、長白色絨毛或切開後內部發黑的情形",
    "verdict": "quality-loss",
    "source_url": "https://www.edh.tw/article/31427",
    "source_date": "2026-08-01"
  }
],
"easily_confused_with": "「發芽」與「發霉腐爛」外觀階段接近，容易混淆。關鍵差異看兩點：①薑體觸感是否仍硬實 ②切開內部是否發黑。發芽無毒只是營養流失，仍可食用；腐爛則可能產生黃樟素（2B類可能致癌物），應整塊丟棄。"
```

- `sign` **必須是具體、可視覺／觸覺／嗅覺辨識的描述**，不能只寫「發霉」「腐爛」這種籠統詞交代過去。要讓使用者能拿著眼前的食材實際對照，寫的時候問自己：「使用者看著食材，要看哪裡、看到什麼樣子，才能對應到這一條？」——顏色（例如「藍黑色斑點」而不是「變色」）、質地（例如「摸起來軟爛出水」而不是「壞掉」）、氣味（例如「散發酸臭味」）都算具體描述；找不到來源裡的具體感官描述時，不要自己編一個，寧可只寫來源裡確實有的部分（例如只寫顏色，不硬湊質地或氣味）。
- `verdict` 只有兩種值，每一條都要明確分類，不可模糊帶過：
  - `discard`：已變質，有食安疑慮的明確徵兆，對應畫面文字「已變質，建議丟棄」
  - `quality-loss`：只是口感／外觀變化，非安全疑慮，通常仍可食用，對應畫面文字「品質下降但通常仍可食用，建議儘快處理」
- `source_url` / `source_date`：查到可靠來源時才填，用於食材詳細頁在變質判斷區塊下方顯示可點擊的「資料來源」連結。**查無可靠來源時，這兩個欄位直接留空，不要為了填欄位硬塞一個不夠格的連結**，該筆食材的 `spoilageSigns` 也建議整個省略，而不是放空陣列或放不確定的內容。
- `easily_confused_with`（食材主體層級，選填）：當這筆食材存在「外觀階段相近、但變質結論相反」的狀態時才填，簡短說明容易跟哪個狀態混淆、關鍵差異在哪，方便之後 UI 做對照式呈現。不是每筆食材都需要這個欄位——只有真的有「看起來很像但結論不同」的風險時才寫，避免每筆都硬湊一段。

### 查證標準（比 selectionTips 更嚴格）

- **只採用具公信力的食品安全衛教內容**：衛福部食藥署（尤其是「食藥闢謠專區」）、農業部「農業知識入口網」（含各區農業改良場官方回覆）、地方衛生局官方頁面，或明確引述上述機關原始說法的主流媒體報導。一般部落格、社群分享、未具名的「網路整理」不算數，即使內容看起來合理也不採用。
- **等級要求 `secondary` 以上**：直接引用政府機關官方頁面（食藥闢謠專區、農業知識入口網等）記為 `official`；媒體報導但有明確引述具名政府機關原始說法、且用詞一致，記為 `secondary`；達不到這個標準的一律不收錄。
- **查無可靠來源時留空、不用一般網路共識填補**：這是本欄位跟 `selectionTips` 最大的差異——`selectionTips` 找不到兩個獨立來源時還可以先用 `unverified` 暫記著，但 `spoilageSigns` 沒有「先猜一個」的空間，寧可整個欄位省略，也不要放不確定的食安資訊。每次新增時，把查無可靠來源的品項回報給使用者，由使用者決定要不要進一步確認。

### 已知具體食安風險的品項要特別仔細核對

某些食材的「能不能吃」判斷背後有具體毒素風險（例如馬鈴薯發芽＋表皮變綠含龍葵鹼），這類資訊寫錯的後果比一般挑選技巧嚴重得多，處理時要額外注意：

- 同一食材常有「看起來很像但風險完全不同」的兩種狀態，要在來源裡明確找到兩者的區分方式，不能憑外觀相似就合併處理。例如薑「只是發芽」（無毒，僅營養流失）跟「發霉腐爛」（可能產生黃樟素，2B 類可能致癌物）外觀階段相近，但食安結論完全不同，必須拆成兩條分別標記，並填寫 `easily_confused_with` 說明關鍵差異。
- 遇到多篇來源說法有出入時，優先採信直接來自政府機關（尤其食藥署／農業改良場）的原始說法，媒體的個案軼事或推測性描述（例如未經證實的單一中毒案例）不應該蓋過官方的整體風險評估。
- 這類欄位建議額外用另一個獨立管道（例如直接搜尋該機關的闢謠頁面或官方問答）交叉確認過一次，才收錄。
- **查證過程中若發現這個風險本質上無法靠外觀／氣味判斷（來源明確寫「無法從外觀辨別」），不要硬塞進 `spoilageSigns`**，改記錄到下方的 `hiddenRisks` 欄位。把「看不出來的風險」放進「看得出來的徵兆」清單裡，是比查無來源更嚴重的錯誤——會讓使用者誤以為自己已經檢查過、安全無虞。

## 隱性風險欄位（hiddenRisks）

`spoilageSigns` 的前提是「這個風險看得出來」，但有些食安風險本質上**無法透過外觀、氣味、觸感判斷**，例如鯖科魚類（鯖魚、鮪魚、正鰹、秋刀魚等）不新鮮時可能產生的組織胺中毒——食藥署官方明確表示這個轉變「發生在腐敗初期，無法經由外觀或氣味辨別」。這種風險如果混在 `spoilageSigns` 的清單裡，會讓使用者誤以為「我檢查過外觀，應該安全」，反而造成危險，所以刻意獨立成一個欄位。

### 結構

```json
"hiddenRisks": [
  {
    "risk": "組織胺中毒（鯖科魚類食物中毒／scombrotoxicosis）：食用後數分鐘至4小時內可能出現臉部潮紅、皮膚紅疹、身體發癢等過敏性中毒症狀，症狀可持續3至36小時",
    "why_not_visible": "魚體中的組胺酸（histidine）在不當保存下經細菌作用轉變為組織胺（histamine），這個轉變發生在腐敗初期，無法經由外觀或氣味辨別",
    "prevention": "購買後全程保持低溫或冷凍狀態、避免溫度回升，是唯一有效的預防方式；沒有任何「看起來還新鮮」的判斷方式可以取代正確冷藏冷凍",
    "source_url": "https://www.fda.gov.tw/tc/newsContent.aspx?cid=5049&id=13769",
    "source_date": "2026-08-01"
  }
]
```

- `risk`：風險是什麼、可能造成的症狀，讓使用者知道嚴重性。
- `why_not_visible`：**這個欄位是 hiddenRisks 存在的理由**，一定要交代清楚為什麼外觀／氣味沒用，不能只是含糊帶過「不容易判斷」。
- `prevention`：正確的預防方式，通常是保存方式（例如全程冷鏈），而不是挑選技巧——因為問題本來就出在「已經買回家、保存過程中才發生」，不是能靠當下挑選避開的。
- `source_url` / `source_date`：跟 `spoilageSigns` 一樣，用於 UI 顯示可點擊的資料來源連結，查無可靠來源時留空。

### 查證標準

跟 `spoilageSigns` 用同一套標準（只採信食藥署／農業知識入口網／學術食品安全資源，等級 `secondary` 以上，查無來源就整個省略），差別只在於歸類到哪個欄位。

### UI 呈現原則

`hiddenRisks` 跟 `spoilageSigns` **未來在畫面上要分開呈現**，不可合併成同一份清單。`spoilageSigns` 可以設計成「你看到這樣→請這樣處理」的對照式呈現；`hiddenRisks` 應該用明顯不同的視覺樣式（例如獨立的警示區塊），並且清楚傳達「這個風險光看外觀防不了，保存方式才是重點」，避免使用者掃過 spoilageSigns 覺得「看起來正常」就放心大意。

### 適用範圍不限單一食材

`hiddenRisks` 記錄的是**這一類食材共通的風險**，不是單一品項的個案。例如組織胺風險理論上適用所有組胺酸含量高的魚種（不限於鯖科分類學上的鯖魚、鮪魚、正鰹，鬼頭刀、旗魚、秋刀魚、沙丁魚等非鯖科魚類不新鮮時也有同樣風險）。日後新增這類魚種時，要主動比照套用同樣的 `hiddenRisks` 內容，不要因為「這筆是新加的」就漏掉。

## 品種（variants）處理邏輯
不是每個食材都要拆品種，**只有品種間「產季」或「挑選技巧」有明顯差異時才拆**（例如芒果、葡萄、地瓜、茶）。若品種只是外觀細節差異、選購邏輯相同，用一句「常見品種：OO、OO」帶過即可。

共用資訊（分類、營養、保存方式）放在食材主體層級，不隨品種變動；產季、外觀、挑選技巧則依品種切換。

```json
{
  "name": "芒果",
  "category": "水果",
  "nutrition": [ /* 共用 */ ],
  "storage": "...",           // 共用
  "variants": [
    { "variant_name": "愛文", "months": [5,6,7,8], "appearance": "...", "selectionTips": ["..."] },
    { "variant_name": "金煌", "months": [6,7,8],   "appearance": "...", "selectionTips": ["..."] }
  ]
}
```

UI 上先用簡單的品種列表／pill 切換即可，不用一開始就做複雜元件。

## 肉品的欄位彈性
肉品沒有現成的公開資料庫，且多為全年供應：
- 產季欄位：直接標「全年供應」或隱藏，不用勉強套產季月曆
- 挑選技巧：先用一組**通用原則**（顏色、油花、彈性、包裝標示、有效期限）套用在整個肉類分類即可，不用每個品項客製化

> 原則：欄位是「有就顯示、沒有就用通用內容或隱藏」的彈性欄位，不是每筆資料都要填滿同一套欄位。

## 內容資料來源
- 營養資料：衛福部食藥署「食品營養成分資料庫」，政府資料開放平台有開放資料集與 API（data.gov.tw/dataset/8543）
- 蔬果產季／產地：農業部資料開放平台（data.coa.gov.tw）、農糧署「農產品產地產期查詢」「水果月曆」
- 海鮮產季：無完整官方資料，需搭配民間整理來源（如食令日曆、天下雜誌台灣四季海鮮指南）交叉驗證
- 肉品：無公開資料庫，挑選原則需自行整理

## 資料驗證分級

食材資料多半先由 AI 協助草擬，品質參差不齊，需要一套機制標示「這筆內容有沒有被查證過、查到什麼程度」。每筆食材的 `nutrition`、`selectionTips`、`months`、`spoilageSigns`、`hiddenRisks`（若有這些欄位）**各自獨立**記錄驗證狀態（因為同一筆食材，營養可能已查證、產季卻還沒），格式為：

```json
"verification": {
  "nutrition": { "level": "official", "source": "..." },
  "selectionTips": { "level": "secondary", "source": "..." },
  "months": { "level": "unverified" }
}
```

### 三個等級的定義

| level | 定義 | 適用欄位 |
|---|---|---|
| `official` | 直接比對政府開放資料 / 官方資料庫的結構化資料，數值一致或已依官方數據修正 | 主要用於 `nutrition`（食藥署食品營養成分資料庫有 API 可查） |
| `secondary` | 找到**至少兩個彼此獨立**的可靠來源（政府機關網站、農會／漁會、主流媒體、專業健康媒體）說法一致；若多篇文章其實互相轉載同一篇原始報導，不算獨立來源 | 主要用於 `selectionTips`（挑選技巧散落在網路文章，沒有結構化 API 可查，只能用交叉比對的方式提高信心） |
| `unverified` | 尚未查證，內容為 AI 草擬或既有知識估算，未對照任何外部來源 | 預設狀態；`months`（產季）目前刻意全部保留在此等級，由使用者親自對照農糧署資料人工核對，不透過網路搜尋自動升級 |

### 查證時的原則
- 品種內任一 variant 缺乏獨立佐證時，整筆（含其他 variant）保守保留在較低等級，不因部分品種查到資料就整體升級
- 查證過程中若發現原本內容與可靠來源有出入（例如判斷部位、量測數值錯誤），應直接修正內容本身，而不是保留錯誤內容卻標記已驗證
- `source` 欄位需具體註明查到的來源（機構名稱、網站、樣本編號等），方便日後回頭複查
