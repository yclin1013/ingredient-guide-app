# 食材資料批次新增流程

> 用途：使用者說「照流程新增 N 種某分類」時，依本文件執行，不需要每次重新討論規則。
> 欄位定義與驗證分級的完整規範見 `DATA_SCHEMA.md`，本文件只講操作流程。

> **文件同步原則**：`DATA_SCHEMA.md` 定義資料欄位與結構，本文件定義查證與操作流程，兩份文件必須保持同步。**未來只要在 `DATA_SCHEMA.md` 新增或修改任何欄位，一定要同步更新本文件對應的查證流程與回報格式，不能只改一邊。** 這正是本文件曾經漏掉 `spoilageSigns`／`hiddenRisks`／`easily_confused_with`／照片處理流程／`subcategory` 好幾個欄位的根本原因（2026-08-20 盤點時發現並修正），導致後續新增食材時，這些欄位沒有被納入查證流程或直接被忽略（例如「茼蒿」資料齊全卻漏配照片，事後才被發現）。

## 1. 品項挑選原則（依分類）

| 分類 | 挑選標準 |
|---|---|
| 蔬菜 | 台灣本產、傳統市場常見、一般家庭常買，不選罕見或進口為主品項 |
| 水果 | 同上：台灣本產、傳統市場常見，不選罕見或進口為主品項 |
| 海鮮 | 台灣近海捕撈或養殖常見品項，不選罕見或以進口為主的海產 |
| 肉品 | 以常見「部位」為單位（例如豬五花、雞腿），不是品種或品牌；不需要像蔬果一樣講究產地 |

## 2. 避免重複

新增前，先讀取該分類現有的資料檔（`mobile/src/data/{分類}.json`），列出已收錄品項的 `id` 與 `name`，新增的品項不可與其重複。

## 3. 確認閘門

品項清單選好後，**先列給使用者確認，不要直接開始搜尋或寫入**。使用者確認後才進行後續的資料搜尋與驗證流程。

## 4. 驗證分級規則

三級制（`official` / `secondary` / `unverified`）定義見 `DATA_SCHEMA.md` 的「資料驗證分級」章節。以下是每個欄位在批次新增流程中的具體查證方式。

### 4.1 營養欄位（nutrition）

透過衛福部食藥署「食品營養成分資料庫」API（data.gov.tw/dataset/8543）逐筆核對，成功比對到官方樣本才標記 `official`，並在 `source` 註明樣本名稱與整合編號。

**海鮮的特殊情況**：該資料庫將海鮮歸類在「魚貝類」，樣本用的是官方／學名（例如「台灣鎖管」對應市場俗稱「透抽」），與市場俗名常常對不上，直接查詢俗名找不到資料是正常現象。遇到這種情況時：

1. **不可以查不到就用網路搜尋的營養數據替代**——營養數值只能來自食藥署資料庫，這是唯一來源。
2. 改用「名稱對應解析」機制（見第 5 節）先找出可能對應的官方名稱／學名，再用候選名稱重新查詢 API。
3. 對應後仍查不到，或名稱對應本身無法確定，該筆營養欄位保留 `unverified`，並在完成後的回報中列出，不可以為了讓欄位好看而編造或估算數字。

**篩選與呈現規則**（完整背景見 `DATA_SCHEMA.md`「營養價值欄位的篩選原則」）：

- 熱量一律列出，即使沒有特別突出也保留。
- 其餘欄位只列真正突出的 1–2 項，且必須用下方「官方宣稱門檻表」判斷，不可憑感覺判斷「應該算高吧」。
- 沒有達標的營養素不寫進 `nutrition`；「尚可」不是可以出現的值。若查證後所有項目都不突出，`nutrition` 只留熱量一項即可，不用勉強湊一個重點。
- 每筆最多列 3 項（熱量 + 最多 2 項突出重點）；同時有多項達標時，優先列「數值 ÷ 門檻」倍數較高的項目。
- 達標時一律標記「良好來源」，不用「含量高」「含量極高」（那對應法規表三「高」宣稱，我們用的是門檻較低的表四「來源」等級，用詞要對應正確等級）。
- **`verification.nutrition.level` 為 `unverified`（查無官方資料庫樣本）時**，即使要標註「感覺上」突出的營養素，也不可用「良好來源」「含量低」這種暗示已查證的字眼，一律用「推估含量較高／較低（未經官方資料庫查證）」這類明確標示為估算的措辭，避免使用者誤以為已查證。

**官方宣稱門檻表**（每 100 公克固體食品，依衛福部「包裝食品營養宣稱應遵行事項」表四「來源／供給／含有」宣稱）：

| 營養素 | 門檻 | 對應資料庫查詢欄位 |
|---|---|---|
| 蛋白質 | ≥ 6 公克 | 粗蛋白 |
| 膳食纖維 | ≥ 3 公克 | 膳食纖維 |
| 維生素A | ≥ 105 微克RE | 視網醇當量(RE) |
| 維生素C | ≥ 15 毫克 | 維生素C |
| 鈣 | ≥ 180 毫克 | 鈣 |
| 鐵 | ≥ 2.25 毫克 | 鐵 |
| 鎂 | ≥ 58.5 毫克 | 鎂 |
| 鋅 | ≥ 2.25 毫克 | 鋅 |

- **低脂肪**（脂肪 ≤ 3 公克／100g，法規表二「低」宣稱門檻）**只在肉品／海鮮類別套用**，蔬菜水果幾乎天生符合這個門檻，標了沒有鑑別度。
- **鉀不在這套門檻依據裡**，不能用鉀判斷是否突出；要呈現鉀的數值時，只能用中性方式（純數字，不加「高」「良好來源」等評語）。
- **糖／含糖量刻意不採用**：已評估過是否要納入這套宣稱門檻邏輯，決定不採用，這是刻意的判斷，不是遺漏（詳見 `DATA_SCHEMA.md` 對應說明）。

### 4.2 挑選技巧（selectionTips）

上網搜尋佐證來源，需要**至少兩個彼此獨立**的可靠來源（政府機關網站、農會／漁會、主流媒體、專業健康媒體）說法一致才標記 `secondary`。判斷「獨立」時要注意：多篇文章如果只是互相轉載同一篇原始報導（例如都引用同一個原始出處、內容幾乎逐字相同），不算獨立來源。

查證過程中若發現原有內容與可靠來源有出入，直接修正內容本身，不要保留錯誤內容卻標記已驗證。

品種（variants）之間，若其中任一品種缺乏獨立佐證，整筆（含其他品種）保守保留在較低等級，不因部分品種查到資料就整體升級。

### 4.3 產季（months / seasonNote）

**一律保留 `unverified`，不透過網路搜尋自動升級**，等使用者親自核對。人工核對時，依分類參考不同來源：

- 蔬菜、水果：農糧署「農產品產地產期查詢」、「水果月曆」
- 海鮮：沒有完整官方資料，改用民間整理資料（如食令日曆、天下雜誌台灣四季海鮮指南）交叉驗證，或請教市場攤商的實地經驗

### 4.4 保存變質徵兆欄位（spoilageSigns）

選填欄位，回答「食材買回家、保存一段時間後，怎麼判斷還能不能吃」，查證標準比 `selectionTips` 更嚴格（完整結構定義、範例與判斷細節見 `DATA_SCHEMA.md`「保存變質徵兆欄位」）：

- **查無可靠來源時整個省略欄位**，不放空陣列、不用一般網路共識或猜測填補；每次新增時，把查無可靠來源的品項回報給使用者，由使用者決定要不要進一步確認。
- **只採信具公信力的食品安全衛教內容**：衛福部食藥署（尤其「食藥闢謠專區」）、農業部「農業知識入口網」（含各區農業改良場官方回覆）、地方衛生局官方頁面，或明確引述上述機關原始說法且用詞一致的主流媒體報導；一般部落格、社群分享、未具名的「網路整理」不算數。
- **等級門檻**：直接引用政府機關官方頁面記為 `official`；媒體報導但有明確引述具名政府機關原始說法、且用詞一致，記為 `secondary`；達不到這個標準的一律不收錄（沒有 `unverified` 這個中間地帶——查不到就是不收錄，不是先放著標記未查證）。
- `sign` 必須是具體、可視覺／觸覺／嗅覺辨識的描述，不能只寫「發霉」「腐爛」這種籠統詞；找不到來源裡的具體感官描述時，不要自己編一個。
- `verdict` 只有兩種值：`discard`（已變質、有食安疑慮，建議丟棄）或 `quality-loss`（品質下降但通常仍可食用），每一條都要明確分類。
- **判斷 `official`／`secondary` 時，先分清楚來源是「雙向直述」還是「單向推論」**：來源本身有沒有同時直接描述「正常／可食用」和「異常／應丟棄」這兩種狀態？雙向直述維持原等級；單向推論（來源只直接寫其中一種狀態，另一種是反推出來的）一律降一級，並在 `source` 註明是推論。
- **不可跨物種套用同一份推論**，即使某物種已有官方文件說明判斷邏輯，也不能直接沿用到其他物種，除非該物種也有自己的來源佐證；沒有專屬佐證的物種寧可留白，不要借用其他物種的原理硬套。
- **已知具體毒素風險的品項要特別仔細核對**（例如馬鈴薯發芽含龍葵鹼）：在來源裡明確找到「看起來很像但風險不同」兩種狀態的區分方式，優先採信政府機關原始說法而非媒體個案軼事，建議額外用第二個獨立管道交叉確認過一次才收錄。
- **查證過程中若發現這個風險本質上無法靠外觀／氣味判斷**（來源明確寫「無法從外觀辨別」），不要塞進 `spoilageSigns`，改記錄到 `hiddenRisks`（見 4.5）。

### 4.5 隱性風險欄位（hiddenRisks）

選填欄位，記錄「無法透過外觀、氣味、觸感判斷」的食安風險（例如鯖科等高組胺酸魚種不新鮮時的組織胺中毒），跟 `spoilageSigns` 刻意分開，UI 上也不可合併呈現（完整結構定義、範例見 `DATA_SCHEMA.md`「隱性風險欄位」）：

- 查證標準跟 `spoilageSigns`（4.4）完全相同：只採信食藥署／農業知識入口網／學術食品安全資源，等級 `secondary` 以上，查無可靠來源就整個省略。
- **這個欄位記錄的是「這一類食材共通的風險」，不是單一品項的個案**：新增屬於同一風險類別的品項時（例如新增其他高組胺酸魚種：鮪魚、正鰹、鬼頭刀、旗魚、秋刀魚、沙丁魚等），要主動比照套用既有的 `hiddenRisks` 內容，不要因為「這筆是新加的」就漏掉。
- 目前資料庫裡只有「鯖魚」有這個欄位（組織胺風險）；新增魚類時，若屬於上述高組胺酸魚種，記得檢查是否要一併加上。

### 4.6 外觀相近但結論不同的說明（easily_confused_with）

選填欄位，只有這筆食材的 `spoilageSigns` 存在「外觀階段相近、但變質結論相反」的風險時才填（例如薑「只是發芽」跟「發霉腐爛」外觀階段接近，但食安結論完全不同），不是每筆都要湊一段。只出現在食材主體層級，簡短說明容易跟哪個狀態混淆、關鍵差異在哪。

### 4.7 肉品的例外規則

肉品的產季與挑選技巧不走上述查證流程：

- **產季**：直接標「全年供應」（`seasonNote: "全年供應"`），不需要驗證，`verification.months` 可直接視為不適用這套查證邏輯（沒有產季可查）
- **挑選技巧**：沿用一組通用原則（顏色、油花、彈性、包裝標示、有效期限）套用在整個肉類分類即可，不用每個部位客製化，也因此不需要像蔬果海鮮那樣逐筆找獨立來源佐證

肉品的 `nutrition`、`spoilageSigns`、`hiddenRisks` 仍照一般規則查證，沒有例外。

## 5. 海鮮的「名稱對應解析」機制

海鮮用市場俗名查食藥署資料庫失敗時，依以下步驟處理，**不可以直接放棄或用網路數據代替官方數值**：

1. **搜尋正式名稱／學名**：上網搜尋該市場俗名對應的正式中文名與學名，優先參考漁業署、水試所（台灣水產試驗所）、魚類資料庫等可靠來源。
2. **列出候選名稱**：搜尋結果可能對應到不只一個名稱或物種，把候選都列出來。
3. **逐一用候選名稱查詢 API**：拿每個候選名稱重新查詢食藥署資料庫，找有沒有比對得上的樣本。
4. **成功對應時**：在該筆資料新增 `aliases` 欄位，記錄「市場俗名、官方名稱、學名」三者對應關係，方便之後重複查詢直接沿用，不用每次重新搜尋。結構：

   ```json
   "aliases": {
     "market_name": "透抽",
     "official_name": "台灣鎖管",
     "scientific_name": "Uroteuthis chinensis",
     "note": "選填，補充對應依據或市場俗名使用情形"
   }
   ```

   並在 `verification.nutrition.source` 註明是依據名稱對應查到的，簡述對應依據（例如：「經查證，市場俗名『透抽』對應學名 Uroteuthis chinensis，即食藥署資料庫樣品『台灣鎖管』」）。
5. **名稱對應以學名為準，不以俗名相似度判斷**——台灣海產常見「一名多種」或「一種多名」的情況（例如透抽／小卷／中卷其實是同一物種依大小分級的俗名；但也存在不同俗名字面相似、實際是不同物種的情況）。判斷對應是否成立，要看學名是否一致，不能只看俗名唸起來像不像。
6. **仍有多個物種可能時，不可自行挑一個**：如果搜尋後發現這個俗名在市場上實際對應多個不同物種（俗名混用），必須改用 `nameResolution` 欄位標記該筆為「名稱待確認」，該筆營養欄位保留 `unverified`，並在回報時列出各候選物種與其差異，交由使用者決定要採用哪一個。結構：

   ```json
   "nameResolution": {
     "market_name": "石斑魚",
     "status": "待確認",
     "note": "簡述為什麼無法確定唯一對應，例如：市場俗名在不同地區／攤商對應到多個物種，尚無法判斷本筆資料具體指哪一種",
     "candidates": [
       { "name": "候選物種俗名或學名", "db_sample": "食藥署資料庫對應樣品名稱（若有）", "calories": "熱量數值（若查得到，選填）", "note": "補充說明（選填）" }
     ]
   }
   ```

   `aliases` 與 `nameResolution` **互斥**：「確定對應」用 `aliases`，「待確認」用 `nameResolution`，不會同時出現在同一筆資料裡。

## 6. variants 使用時機

不是每個食材都要拆品種，**只有品種間「產季」或「挑選技巧」有明顯差異時才拆**（例如芒果的愛文／金煌／玉文、葡萄、地瓜、茶）。若品種只是外觀細節差異、選購邏輯相同，用一句「常見品種：OO、OO」帶過即可。海鮮、肉品通常不需要使用 variants 結構。

共用資訊（分類、營養、保存方式）放在食材主體層級，不隨品種變動；產季、外觀、挑選技巧則依品種切換。UI 上先用簡單的品種列表／pill 切換即可，不用一開始就做複雜元件。

## 7. 食材照片處理流程

**重要**：JSON 資料裡的 `image` 欄位目前沒有被程式實際用來顯示照片（是舊有的死欄位）。畫面上食材照片的顯示，實際上是靠 `mobile/src/data/ingredientPhotos.ts` 裡的 `INGREDIENT_PHOTOS` 對照表（以食材 `id` 為 key，`require()` 對應圖片檔案）。**新增食材資料時，如果沒有同步把 `id` 加進這個對照表，畫面上只會顯示分類圖示佔位，不會報錯，非常容易被忽略**（曾發生過「茼蒿」資料齊全卻漏掉配圖、沒被發現的實際案例）。

- 目前這批食材照片是從 `picture/` 目錄下的參考圖裁切而成（暫時性質、非實拍照片，之後會替換成真正的實拍照片），裁切後的檔案放在 `mobile/assets/ingredient-photos/{id}.jpg`。
- 新增食材資料時，若手邊沒有現成的參考圖可裁切，該筆資料先不加入 `INGREDIENT_PHOTOS` 對照即可（畫面會自動顯示分類圖示佔位），**但完成後回報時要明確列出「這批新增的食材目前都還沒有照片」**，不要讓這件事無聲無息地被漏掉（見第 9 節回報格式）。
- 之後有實拍照片可以替換時，直接更新 `mobile/assets/ingredient-photos/{id}.jpg` 檔案內容即可，`ingredientPhotos.ts` 的 `require` 路徑不需要跟著改（檔名維持一致）。

## 8. subcategory 使用時機

`subcategory` 是選填欄位，用途是在同一個食材名稱底下，標示更精確的品種／類型。跟 `variants` 不同：`variants` 是「同一筆資料底下依品種切換產季／挑選技巧」的資料結構，`subcategory` 單純是分類標籤，不影響資料切換邏輯。

- **使用時機**：食材的市場俗名比較籠統，而實際目前查證收錄的內容是以某個明確單一品種為準時，用 `subcategory` 標註實際品種，方便使用者理解。例如：
  - 「柿子」`subcategory` 標「甜柿」——因為目前只收錄甜柿這個品種、沒有需要脫澀處理的澀柿。
  - 「香瓜」`subcategory` 標「美濃瓜」——因為兩者是同一物種的不同俗稱，標註幫助使用者對照市場常見說法。
  - 「小番茄」`subcategory` 標「聖女番茄」——因為目前查證的營養／挑選資料都是以聖女番茄樣本為準。
- 如果同一食材底下未來要收錄「多個」不同品種、且各品種產季或挑選技巧有明顯差異，改用 `variants` 結構（見第 6 節），不要疊加多個 `subcategory`。
- 不確定該不該用時，預設不加這個欄位即可，不是每筆資料都需要。

## 9. 完成後回報格式

全部品項處理完後，回報以下部分：

1. **每筆資料的驗證狀態總覽**：一張表列出每個品項在 `nutrition` / `selectionTips` / `months` 三個欄位各自的驗證等級；若該筆有查證 `spoilageSigns` 或 `hiddenRisks`，一併列出其驗證等級，沒有這兩個欄位的品項該欄位標示「—」（代表這次沒有查到可收錄的來源，不是查證失敗或忘記做）。
2. **海鮮名稱對應狀態**（僅海鮮）：若有品項使用了 `aliases` 或被標記 `nameResolution`（待確認），列出對應結果或候選清單。
3. **照片狀態**：明確列出這批新增品項裡，哪些已經有配對照片、哪些還沒有，不要讓照片缺漏的狀態被隱藏在資料裡沒人發現。
4. **建議優先人工查證的項目**：哪些品項驗證狀態偏弱（例如整筆都是 `unverified`、名稱對應不確定被標記「待確認」、或查無可靠來源因此省略了 `spoilageSigns`／`hiddenRisks`），列出來提醒使用者優先處理。
